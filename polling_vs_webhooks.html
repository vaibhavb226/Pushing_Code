Sysco RFP AIQ · Architecture Decision

Polling vs Webhooks
for Email Detection

Microsoft Graph API · Backend Strategy · July 2026

How It Works Today

The backend runs a polling loop defined in services/email_poller.py. Every 15 seconds it wakes up and asks Microsoft Graph whether any new emails have arrived.

Server wakes up every 15 seconds
→ GET /v1.0/users/{userId}/mailFolders/Inbox/messages?$filter=isRead eq false
→ Processes any new emails found (match → bid, no match → unmatched)
→ Marks each email as read
→ asyncio.sleep(15)
→ Repeat forever

Side-by-Side Comparison

⏱ Polling (Current)

Advantages

  • ProWorks on localhost — no public URL needed
  • ProAuto catches up after server restart
  • ProNo subscription lifecycle to manage
  • Pro/api/email/poll-now for manual trigger
  • ProResilient — downtime never loses emails

Disadvantages

  • ConUp to 15 second delay per email
  • ConBurns API quota every 15s even when idle
  • ConScales poorly with multiple mailboxes
⚡ Webhooks (Graph Change Notifications)

Advantages

  • ProReal-time — email processed in < 1 second
  • ProZero wasted API calls — Graph calls you
  • ProScales cleanly to any volume
  • ProIndustry standard for production systems

Disadvantages

  • ConNeeds a public HTTPS URL (no localhost)
  • ConSubscription expires every 3 days — must renew
  • Con10-second validation handshake on registration
  • ConStill needs a catch-up poll as fallback
  • ConMore complex setup (~4–5 hours of work)
⚖️

Verdict

Webhooks are better for production. Polling is better for development. For the current phase of Sysco RFP AIQ — still in active development with no public URL — polling is the right choice. A 15-second delay is acceptable for a bid management tool and polling requires zero additional infrastructure. Switch to webhooks once the app is deployed to a public HTTPS endpoint and real-time visibility becomes a user requirement.

Cost Comparison

Microsoft Graph webhook subscriptions are free — they are part of the standard Microsoft 365 / Azure AD API with no additional billing. The only costs are infrastructure you would need anyway in production.

ItemCostNotes
Graph API webhook subscriptions Free Included in M365 / Azure AD — no separate billing
Graph API polling calls Free But burns 5,760 quota calls/day even when idle
Public HTTPS server (production) Hosting cost Same server needed for any deployment — not webhook-specific
ngrok (local dev with webhooks) Free tier / ~$8/mo paid Only needed during local webhook testing; not required in production
API quota savings (webhooks vs polling) Saves quota Webhooks use near-zero idle calls vs 5,760/day for polling

Bottom line: Webhooks cost less to run because they don't waste API quota. The only new cost is an ngrok tunnel if you want to test webhooks locally, and that's optional — just keep polling during development.

When to Use Each

Scenario Best Choice Reason
Running locally on a laptop Polling No public URL available — webhooks physically cannot work
Development / testing Polling Simpler, no ngrok setup, instant /poll-now debugging
Proof of concept / demo Polling Already working, no extra setup needed
Deployed to Azure / AWS Webhooks Public URL available — webhooks eliminate delay and quota waste
Production with real users Webhooks 15s delay becomes noticeable in live bid workflow; real-time matters
Multiple mailboxes Webhooks Polling costs multiply per mailbox; webhooks stay flat

Key Implementation Details

1 — Validation Handshake (routers/webhooks.py)

When you register a webhook subscription, Graph immediately sends a test request with a validationToken. Your server must echo it back as plain text within 10 seconds — otherwise the subscription fails.

# routers/webhooks.py — new file
@router.post("/graph")
async def graph_webhook(request, validationToken=Query(None)):
    # Step 1: Echo the token back — must happen within 10 seconds
    if validationToken:
        return PlainTextResponse(validationToken, media_type="text/plain")

    # Step 2: Real notification — process new email
    body = await request.json()
    for notification in body.get("value", []):
        await _process_notification(notification)

2 — Subscription Registration (services/email/msgraph_provider.py)

On startup, register your webhook URL with Microsoft. The subscription lasts a maximum of 3 days for mail resources — it must be renewed automatically.

# New method in MsGraphEmailService
async def create_subscription(self, webhook_url: str) -> str:
    token = await self._get_token()
    payload = {
        "changeType": "created",
        "notificationUrl": f"{webhook_url}/api/webhooks/graph",
        "resource": f"users/{self._user_id}/mailFolders/Inbox/messages",
        "expirationDateTime": (now + timedelta(days=3)).isoformat()
    }
    # POST to https://graph.microsoft.com/v1.0/subscriptions
    return response["id"]  # store this for renewal

3 — Auto-Renewal (main.py)

Add a renewal job to the existing APScheduler instance. Set it to renew every 48 hours so the 3-day subscription never lapses.

# Add alongside the existing "auto_reminders" job in main.py
scheduler.add_job(
    renew_graph_subscription,
    "interval",
    hours=48,          # renew every 2 days — subscription max is 3
    id="graph_sub_renewal"
)
